# Passvault protocol (Phase 1, native realm)

This is the reference the code comments point to. It describes the
zero-knowledge crypto protocol implemented in `web/crypto.js` (client) and
`internal/crypto` / `internal/auth` (server). See README.md for the phased
roadmap — this file is just the crypto protocol, kept precise enough to
re-implement a client against.

The server never sees a master password or a usable key. Everything below
that's marked "client-only" never appears in a request body, a response
body, a database row, or a log line.

## Threat model boundary: passive vs. active server compromise

This guarantee is airtight against **passive** compromise — someone with
full read access to the database, the filesystem, or network traffic
(a stolen backup, a subpoenaed disk image, a passive network tap) learns
nothing usable: every row is either opaque ciphertext or a value that
provably can't be reversed into a master password or key (see "What
`opaque to the server` actually means" below).

It does **not** extend to **active** compromise of the server process
itself. Passvault is a browser-delivered web app: the same server that
would need to be compromised to steal data is also the one serving
`app.js`/`crypto.js` to the browser on every page load. Anyone who can
modify those served files — a malicious operator, or an attacker who's
gained code-execution on the host — can serve a version that exfiltrates
the typed master password or a derived key the instant a targeted
victim's browser loads it, silently and per-target if desired. No
cryptographic primitive in this codebase can detect or prevent that,
because the attacker controls the code that would need to do the
detecting. This is not a Passvault-specific gap — it's inherent to any
E2EE product delivered as a web app rather than a native/signed client
(Bitwarden's own web vault, Proton Mail's webmail, and Signal Web all
carry the identical caveat) — but it means "malicious server operator"
in `SECURITY.md`'s scope is fully defeated only for the passive case.
There is currently no self-hoster-facing way to verify a served build
against a known-good hash (no subresource integrity, no signed-release
diffing) — treat that as a known gap, not a solved problem.

## KDF

`Argon2id(masterPassword, salt, memoryKiB=65536, iterations=3, parallelism=4) -> masterKey (32 bytes)` — client-only.

`salt` is random, generated by the client at signup (`crypto.getRandomValues`,
16 bytes, base64) — never derived from email, to avoid tying KDF cost to a
guessable identifier. The server stores `salt` + the three cost parameters
per user and returns them unauthenticated from `GET /v1/auth/prelogin` so a
client can recompute the same `masterKey` before it has sent anything.

## Two subkeys, one HKDF-SHA256 run each

```
authKey = HKDF-SHA256(ikm=masterKey, salt="", info="passvault-auth-v1", len=32)   // sent to server
wrapKey = HKDF-SHA256(ikm=masterKey, salt="", info="passvault-wrap-v1", len=32)   // client-only
```

`authKey` is sent to the server at register/login. The server never stores
it directly — it stores `Argon2id-2(authKey)` (a second, server-parameterized
Argon2id round, `internal/crypto.HashAuthKey`). This isn't brute-force
defense (authKey already has ~256 bits of entropy) — it means a stolen DB
row alone is not a usable login credential; reproducing `authKey` still
requires the master password.

`wrapKey` never leaves the client. Its only job is wrapping/unwrapping
`vaultKey`.

## Vault key envelope

At signup the client generates one random 256-bit `vaultKey` (client-only,
forever) and wraps it:

```
wrappedVaultKey = AES-256-GCM-Encrypt(key=wrapKey, plaintext=vaultKey)   // 12-byte random IV || ciphertext+tag, base64
```

`wrappedVaultKey` is the only thing derived from `vaultKey` that the server
ever stores. Everything else (folders, ciphers) is encrypted under
`vaultKey` indirectly, through a per-item key — never directly under
`wrapKey`.

**Password change** (`internal/auth.ChangePassword`, gated by
`HandleChangePassword`): the client derives a *new* `wrapKey'` from the new
master password (same KDF, new or same salt), re-wraps the *same*
`vaultKey` under it, and uploads the new `wrappedVaultKey'` plus new
`Argon2id-2(authKey')`. One atomic UPDATE. No cipher or folder is touched,
because `vaultKey` itself never changed — this is the entire point of
wrapping instead of directly encrypting data with a password-derived key.

Holding a valid access token is deliberately **not** sufficient to reach
`ChangePassword` — `HandleChangePassword` first re-verifies the *current*
`authKey` server-side (`auth.VerifyCurrentAuthKey`) and a live 2FA code if
one is enabled, the same step-up bar as the account recovery kit below.
Without this, a bearer token leaked in isolation (an XSS bug, a malicious
extension, a logged header) could be escalated into overwriting
`wrappedVaultKey` with attacker-chosen garbage — a one-shot, unrecoverable
destruction of the account's own vault, since the server has no way to
tell a legitimate re-wrap from a malicious one; it never sees `vaultKey`
either way. On success every device but the one that just proved the new
password is revoked (`auth.RevokeAllDevicesExcept`) and the account gets a
"your password was changed" email — a stolen token and a genuine change
can't be told apart on whether *other* sessions should keep working, so
they don't get the benefit of the doubt.

## Per-item envelope

Every folder and cipher gets its own random 256-bit `itemKey`:

```
wrappedItemKey = AES-256-GCM-Encrypt(key=vaultKey, plaintext=itemKey)
encryptedBlob  = AES-256-GCM-Encrypt(key=itemKey, plaintext=JSON({name, username, password, totp, notes, uris, ...}))
```

The server stores and relays `wrappedItemKey` and `encryptedBlob` verbatim
(`internal/api` cipher/folder handlers only validate they're non-empty,
valid base64, under a size cap — never decrypt them, because they can't).

Rotating one item's key (e.g. after a suspected leak of that one item) only
touches that item's row.

## X25519 keypair (generated Phase 1, used for item sharing)

Every user gets an X25519 keypair at signup so sharing never needs a
disruptive later migration:

```
(pubKey, privKey) = X25519.generateKeyPair()          // client-only until wrapped
wrappedPrivKey    = AES-256-GCM-Encrypt(key=vaultKey, plaintext=privKey)
```

`pubKey` is stored in cleartext (anyone sharing an item *to* this user
needs it); `wrappedPrivKey` follows the same envelope rule as everything
else — only usable after `vaultKey` is unwrapped, i.e. only after a
successful login.

### Item sharing (implemented)

Simple, one-item-at-a-time sharing — no orgs, no collections, no
group/role model. Owner and recipient each independently compute the same
shared secret; nothing keyed is ever transmitted:

```
sharedSecret   = X25519.ECDH(myPrivKey, theirPubKey)     // == ECDH(theirPrivKey, myPubKey)
shareWrapKey   = HKDF-SHA256(ikm=sharedSecret, salt="", info="passvault-share-v1", len=32)
wrappedItemKey = AES-256-GCM-Encrypt(key=shareWrapKey, plaintext=itemKey)   // itemKey unchanged, same one the owner already uses
```

The owner looks up the recipient's `pubKey` by email
(`GET /v1/users/lookup`), computes `wrappedItemKey`, and POSTs it
(`internal/api/share_handlers.go`, table `cipher_shares`). The recipient's
`GET /v1/sync` response includes a `shared_ciphers` array carrying the
owner's `pubKey`, the item's `encryptedBlob`, and this share-specific
`wrappedItemKey` (distinct from the owner's own `vaultKey`-wrapped copy in
`ciphers.wrapped_item_key`) — the recipient redoes the ECDH on their side
to unwrap it. Revoking a share is a hard delete of the `cipher_shares` row;
since shares aren't part of the incremental `revision_ts` delta-sync, a
recipient's next `GET /v1/sync` simply stops including it — no tombstone
needed. Removing a member's access does *not* rotate the item's own key
(unlike an org-key model) — this is the accepted "simple sharing" scope,
matching the plan's phase-3-lite scope decision, not a Phase-3 org rewrite.

## Passkey unlock (device-local, implemented)

An opt-in convenience that lets one browser skip retyping the master
password using a platform authenticator (Touch ID, Windows Hello, a
security key), via the WebAuthn **PRF extension**. This is *not* a second
authentication path — the server is never told about the passkey and never
trusts it for anything; it exists purely to derive a real, deterministic,
hardware-bound symmetric secret that can wrap/unwrap material the client
already obtained from a normal password login.

```
prfSecret (32 bytes) = WebAuthn PRF eval(credential, salt="passvault-passkey-unlock-v1")   // client-only, platform-authenticator-bound
passkeyWrapKey        = HKDF-SHA256(ikm=prfSecret, salt="", info="passvault-passkey-unlock-v1", len=32)
cachedBlob             = AES-256-GCM-Encrypt(key=passkeyWrapKey, plaintext=JSON({vaultKey, x25519PrivateKey, refreshToken}))
```

`cachedBlob` plus the WebAuthn credential id are stored in this browser's
`localStorage` only (`web/app.js`'s `PASSKEY_STORAGE_KEY`, keyed by email)
— never sent to, or derivable by, the server. Unlocking re-evaluates the
PRF extension against the *same* credential and salt (deterministic: the
authenticator returns an identical output every time), re-derives
`passkeyWrapKey`, decrypts `cachedBlob`, and exchanges the cached
`refreshToken` at `POST /v1/auth/refresh` for a fresh token pair. Refresh
tokens are single-use and rotate on every exchange (`internal/auth.Refresh`),
so the new one is immediately re-wrapped and re-persisted, or the *next*
unlock on that device would fail.

Because this wraps `vaultKey` directly rather than a password-derived key,
changing the master password (which re-wraps `vaultKey` under a new
`wrapKey'` but never changes `vaultKey` itself) does not invalidate an
existing passkey enrollment. A future "rotate vault key" panic action
(not yet implemented) would need to explicitly clear it, since that *does*
replace `vaultKey`.

Losing the device, clearing that browser's storage, or an authenticator
that doesn't support the PRF extension all just mean falling back to the
master password — there is no server-side state to clean up, by design.

## Send (one-time/expiring anonymous links, implemented)

A Send lets a recipient with **no Passvault account at all** decrypt one
piece of content (text or a file) via a plain URL. Its content is
encrypted under its own fresh random `sendKey` — not `vaultKey`, not an
`itemKey` — because the recipient has nothing else to derive a key from:

```
sendKey (32 bytes) = random, generated client-side at creation
encryptedContent    = AES-256-GCM-Encrypt(key=sendKey, plaintext=JSON({text}))          // text Sends
                    | AES-256-GCM-Encrypt(key=sendKey, plaintext=fileBytes)              // file Sends (raw bytes, not JSON)
wrappedSendKey      = AES-256-GCM-Encrypt(key=vaultKey, plaintext=sendKey)               // lets the OWNER re-derive sendKey later
encryptedLabel      = AES-256-GCM-Encrypt(key=vaultKey, plaintext=JSON({label}))         // owner-only note, same envelope as folders.encrypted_name
```

`sendKey` itself is given to the recipient by embedding it — url-safe
base64 (`web/crypto.js`'s `toURLSafeB64`), never standard base64 — in the
share URL's **fragment**: `.../send.html#<send id>.<sendKey>`. A URL
fragment is never sent in the HTTP request line, headers, or logged by
any standard web server or proxy, which is what makes it (not a query
parameter, not the path) the only correct place for a raw key that must
never reach the server. `web/send.js` is the entire recipient-side trust
boundary: no login, no session, no `vaultKey` — it reads the fragment,
fetches ciphertext by id, and decrypts locally.

The owner's own client can *also* always recover `sendKey`, via
`wrappedSendKey` + their already-unlocked `vaultKey` — independent of
still having the original URL — which is what lets "My Sends" offer
re-viewing/re-downloading content and regenerating the share link at any
time (`internal/api/send_handlers.go`'s `HandleDownloadOwnSendContent`).

**Optional password** (`sends.password_hash`, `crypto.HashAuthKey` reused
as a generic Argon2id hash — it isn't actually an authKey here, just the
same primitive): a *separate* server-side gate checked before any
ciphertext is released, independent of `sendKey`. Be precise about what
this does and doesn't defend against — it stops someone who merely has
the URL (browser history, a shoulder-surf, a referrer leak) but doesn't
know the separately-shared password; it does **not** add cryptographic
protection against a compromised server, which could withhold the
password check but still return the same ciphertext to itself. A failed
password attempt is rejected before the view-count claim below, so
guessing wrong never burns a limited Send's remaining views.

**View limit / burn-after-reading** (`sends.max_views`): claimed via a
single atomic `UPDATE ... WHERE view_count < max_views RETURNING ...` in
`HandleAccessSend`, so two simultaneous requests against a Send with one
view left can't both succeed — Postgres's row lock during the `UPDATE`
serializes them. Exhausting the limit deletes the Send (row + any on-disk
file) immediately. A Send that instead just times out unread is caught by
`SweepExpiredSends`, run once at boot and hourly thereafter
(`cmd/passvault-server/main.go`) — no external cron dependency.

**Scheduled reveal / time-delay** (`sends.available_at`, optional):
distinct from `expires_at` — a Send with this set *exists* and its
metadata is visible immediately (`GET /public/sends/{id}` includes it, so
`web/send.js` can show "unlocks at &lt;time&gt;" instead of making a
recipient guess by trying and failing), but `HandleAccessSend` refuses to
release content — `425 Too Early` — until `now()` reaches it, checked
*before* the password so a premature attempt never burns a rate-limit
attempt against real content. Must land strictly before `expires_at`
(rejected at creation otherwise), or the Send would become reachable and
already-expired in the same instant. A dead-man-switch / "don't open
before Monday" primitive, not a delivery delay — the link is fully live
and copyable the moment it's created.

## Emergency access (implemented)

Bitwarden-style: a grantor designates a trusted contact (an existing
Passvault account, by email) who can request "view" (read-only) or
"takeover" (full account reset) access if the grantor ever goes
unreachable. State machine: `invited → accepted → confirmed → requested →
granted`, with `requested` reverting to `confirmed` on rejection
(`internal/api/emergency_access_handlers.go`, table `emergency_access` in
`internal/db/db.go`).

Only ONE step ever touches key material — **confirm**, and only the
grantor's own client can do it, since only they have `vaultKey` unwrapped:

```
sharedSecret       = X25519.ECDH(grantorPriv, granteePub)   // == ECDH(granteePriv, grantorPub)
emergencyWrapKey    = HKDF-SHA256(ikm=sharedSecret, salt="", info="passvault-emergency-v1", len=32)
wrappedVaultKeyForGrantee = AES-256-GCM-Encrypt(key=emergencyWrapKey, plaintext=grantorVaultKey)
```

This is deliberately the *same shape* as item sharing's `deriveSharedWrapKey`
(`web/crypto.js`) but with its own HKDF info string (`deriveEmergencyAccessWrapKey`)
— the same two accounts' raw ECDH output must never be reusable as key
material across the two features, even though the underlying X25519 math
is identical. Every other transition (invite, accept, request, reject,
approve) is a plain status change with no crypto at all.

Once `status='granted'`:
- **View**: the grantee's client fetches the grantor's current
  folders/ciphers (`GET /v1/emergency-access/{id}/vault`, shaped like a
  one-shot sync) plus `wrappedVaultKeyForGrantee` and the grantor's public
  key, redoes the ECDH, unwraps `grantorVaultKey`, and decrypts each item
  exactly like a shared item (reusing `renderSharedItem` client-side).
- **Takeover**: the grantee, having recovered `grantorVaultKey` the same
  way, picks a *new* master password **for the grantor's account**,
  derives a fresh `wrapKey'` from it (the grantor never enters anything —
  the grantee's client does the KDF), and re-wraps the *same*
  `grantorVaultKey` under it — identical reasoning to `auth.ChangePassword`
  for why this never touches a single cipher or folder. The server then
  revokes every one of the grantor's existing device sessions
  (`auth.RevokeAllDevices`) — the old password no longer controls the
  account, so nothing that only knew it should keep working — and emails
  the grantor a security notice.

A request whose wait period elapses without the grantor rejecting it is
auto-granted by `SweepEmergencyAccessGrants`, run on the same hourly
ticker as `SweepExpiredSends`.

## Account 2FA (implemented)

TOTP required at login, in addition to the master password — a genuinely
different thing from a vault item's own stored TOTP (client-only,
web/totp.js) or from passkey unlock (a device-local convenience on top of
an already-authenticated session): this gates the login ceremony itself.

The secret (`users.totp_2fa_secret`) is necessarily server-side — the
server has to actively compute and compare a code on every login, which
is impossible if the secret were only recoverable after a successful
login — same "operational, not zero-knowledge" trust class as
`smtp_settings.password`. Verification is RFC 6238 (SHA-1/6 digits/30s,
±1 step clock-skew tolerance) via `internal/totp`, checked against the
real published RFC 6238 Appendix B test vector, not just a self-consistency
round-trip.

Login becomes two HTTP round trips once 2FA is on:

```
POST /v1/auth/login            (authKey correct, 2FA enabled)
  -> { requires_2fa: true, login_challenge }        // NOT a token pair yet
POST /v1/auth/login/2fa        (login_challenge, code)
  -> normal login response (device tokens, wrapped_vault_key, ...)
```

`login_challenge` (`pending_logins` table) is short-lived (5 minutes) and
good for up to 10 code attempts within that window — a wrong digit burns
an attempt, not the whole challenge, so a typo doesn't force retyping the
master password too (this was a real bug caught during testing: the
initial implementation deleted the challenge on ANY attempt, correct or
not). 10 one-time recovery codes are issued whenever 2FA is enabled or
explicitly regenerated (invalidating the previous batch); a recovery
code substitutes for a TOTP code at login and its use triggers a
security-notice email, since it's a plausible signal of a compromised
password.

A verified TOTP code can't be replayed within its own ±1-step (~90s)
window: every call site that treats a code as authorization — login's
second phase, disabling 2FA, regenerating recovery codes, changing the
master password, touching the recovery kit — uses `totp.VerifyStep` and
then atomically claims the matched time-step counter via
`auth.ConsumeTOTPStep` (`users.totp_last_used_step`, monotonic). Only the
step number is ever persisted, never the code itself; `totp.Verify` alone
stays a pure, replay-agnostic primitive with no such guard, used only for
`HandleEnable2FA`'s one-time setup confirmation where replay doesn't
apply. `verifyCurrent2FA` (the shared helper behind the four
already-authenticated call sites) is also rate-limited per user —
otherwise a hijacked session token without the TOTP secret could hammer
the 6-digit space with no throttle at all.

## Email alias generation (implemented)

An optional per-account integration with a third-party alias provider
(SimpleLogin today) so a generated login's "email" field can be a fresh
alias instead of the real address. The provider's API key is
AES-256-GCM-encrypted under the account's own `vaultKey`
(`users.wrapped_email_alias_api_key`) — zero-knowledge at rest, synced
across the account's devices the same way any other wrapped blob is.

It cannot stay zero-knowledge *in transit* for the one call that actually
creates an alias: SimpleLogin's API does not set CORS headers permitting
a browser to call it directly (`internal/api/email_alias_handlers.go`'s
comment records this as verified empirically — a live `fetch()` from a
foreign origin — not assumed from their docs). The client decrypts the
key locally and sends it to `POST /v1/email-alias/generate`, a thin proxy
that uses it for exactly one outbound request and never logs, stores, or
otherwise retains it.

## Account recovery kit (implemented)

The mitigation for the one real cost of zero-knowledge design: there is no
server-side "forgot password" reset, so losing the master password with
no emergency-access trusted contact set up means permanent lockout. A
recovery kit is a one-time, print-and-store-offline alternative, and it
deliberately mirrors the master password's own two-value split:

```
recoveryCode (32 bytes)      = random, client-only, shown to the user exactly once
recoveryAuthKey               = HKDF-SHA256(recoveryCode, info="passvault-recovery-auth-v1", 32)   // sent to server as a verifier
recoveryWrapKey                = HKDF-SHA256(recoveryCode, info="passvault-recovery-wrap-v1", 32)   // client-only
wrappedVaultKeyForRecovery     = AES-256-GCM-Encrypt(key=recoveryWrapKey, plaintext=vaultKey)
```

`recovery_code_hash` (`crypto.HashToken(recoveryAuthKey)` — cheap, not
Argon2id, since recoveryAuthKey already carries 256 bits of entropy, same
reasoning as `recovery_codes.code_hash` for 2FA) is what keeps the
"forgot password" endpoint from being a free-for-all "reset anyone's
password" endpoint: only someone who can reproduce `recoveryAuthKey` —
i.e. who actually has the printed code — gets back
`wrappedVaultKeyForRecovery` at all (`POST /v1/auth/recovery/verify`,
rate-limited like a login attempt). A short-lived, single-use-on-success
challenge (`pending_recoveries`, mirroring `pending_logins`) then bridges
that to `POST /v1/auth/recovery/finish`, which sets a new master password
using `auth.ChangePassword`'s usual re-wrap-the-same-vaultKey trick — no
cipher or folder is touched — and revokes every existing device, same as
an emergency-access takeover.

If the account has 2FA enabled, the recovery kit alone is **deliberately
not enough** to finish recovery — a TOTP or 2FA-recovery code is also
required, checked with the exact same acceptance logic as login's second
phase. Without this, a stolen printed recovery kit would bypass 2FA
entirely, which would defeat the point of having it. Creating a new kit
overwrites (invalidates) any previous one, and a kit is *not*
auto-regenerated after a successful recovery — the user must deliberately
make a new one.

Creating, replacing, or removing a kit (`HandleSetRecoveryKit` /
`HandleDeleteRecoveryKit`) all require the same step-up re-authentication
as a password change — the current `authKey` re-verified server-side, plus
a live 2FA code if enabled — even though the caller already holds a valid
access token. This endpoint writes the exact `recoveryAuthKey`/
`wrappedVaultKeyForRecovery` pair that `HandleVerifyRecovery` /
`HandleFinishRecovery` later accept, unauthenticated, as sufficient to
reset the master password outright: without the re-auth gate, a bearer
token leaked in isolation could plant a takeover backdoor (on an account
without 2FA) or silently destroy the real kit, neither of which should be
reachable by anything short of the master password itself.

## Import / export (implemented)

`web/importexport.js` is deliberately pure — no DOM, no network, no
crypto — because it only ever handles **plaintext** item data, by
definition: an export is already-decrypted content about to leave the
browser, an import is not-yet-encrypted content that just arrived. That
separation is what keeps it safe to reason about independently of
`crypto.js`'s actual trust boundary.

**Export** reads directly from what's already decrypted in memory
(`itemsById`/`folders` — no extra `/v1/sync` round trip) and triggers a
plaintext `.json` download. There is no way to make an export of readable
data not be plaintext, so the one real safeguard is a **local
re-authentication gate**: before export proceeds, the typed master
password is re-derived into `wrapKey` and used to unwrap the account's
own `wrapped_vault_key` — no server round trip needed, since
`session.user` already carries it from login. A wrong password fails the
AES-GCM tag check inside `unwrapKeyBytes` and export never runs. Without
this, a hijacked-but-already-unlocked browser tab could silently dump the
entire vault with one click.

**Import** parses a file into a normalized `{type, folder, fields}[]`
shape, shows a preview (item-type counts, per-item warnings) before
touching anything, then — on confirm — encrypts and uploads each item
exactly the way the "Add item" form already does: a fresh `itemKey` per
item, wrapped under `vaultKey`, one `POST /v1/ciphers` per item. A folder
named in the file that doesn't already exist is created once (not once
per item that references it) via the same endpoint the folder-creation
form uses. Three source formats are supported today:

- **Passvault (JSON)** — this app's own export format, for a clean
  round-trip between instances.
- **Bitwarden (JSON)** — built directly against Bitwarden's own
  documented export schema (`folders[]` + `items[]`, numeric `type` 1-4
  for login/note/card/identity), not guessed. A Passvault file selected
  under this format is explicitly rejected with a clear message rather
  than silently importing zero items, since both formats have a top-level
  `items` array and would otherwise pass a naive shape check.
- **Chrome / Google Password Manager (CSV)** — the plain
  `name,url,username,password,note` export, parsed with a small
  RFC-4180-ish CSV parser (handles quoted fields with embedded commas/
  newlines) rather than a naive `split(",")`, since real password/note
  values routinely contain commas.

Login items gained a `uri` field as part of this work — previously
nothing in the schema had anywhere to put a saved website URL at all,
which would have silently dropped that data on every import from a
format that has it (every format does).

## PWA / offline support (implemented)

Two independent pieces, deliberately kept separate so "what persists
offline" stays auditable in exactly one place per concern:

**App shell caching** (`web/sw.js`, `web/manifest.json`) makes the static
app installable and loadable without a network connection at all —
`index.html`, every `.js` module, the vendored Argon2id WASM, and the
icon set are precached on service-worker install. The fetch handler is
**network-first, not cache-first**: it always tries the network and only
falls back to the cache on failure, so a redeployed build reaches an
already-open tab on its next reload instead of being stuck on stale
cached JS indefinitely. The service worker's fetch handler uses an
explicit **allowlist** — same-origin GET only, and it bails out
immediately for anything under `/v1/` or `/public/` — rather than a
denylist, so a new API route added later is safe-by-default (passes
straight to the network untouched) instead of silently getting cached
because nobody remembered to list it.

**Vault data offline fallback** (`web/app.js`) is unrelated to the
service worker and has no opinion from it. On every successful
`GET /v1/sync`, the raw response is mirrored into `localStorage` — still
exactly the same opaque ciphertext the server already sent over the
wire, nothing decrypted or re-derived, the identical trust boundary as
every other blob this app persists. If a later sync call fails (offline,
or the server genuinely unreachable), `refreshItems()` falls back to
that cached response and shows a banner ("You're offline — showing your
last synced vault") instead of crashing or showing a raw fetch error.
This only helps an **already-unlocked** session: `session.vaultKey` stays
memory-only by design (see the top-of-file comment in `app.js`), so a
full page reload always requires logging back in regardless of what's
cached, offline or not. Separately, `api()` fails fast with a clear
"You're offline" message when `navigator.onLine` is false, rather than
letting every caller hit a slow, confusing generic fetch failure.

## Browser extension (implemented: login + autofill; passkeys not yet)

`extension/` (Manifest V3, Chromium) reuses the exact same client crypto as
the web app — `extension/lib/crypto.js` is a generated copy of
`web/crypto.js` with `export` keywords stripped (see
`scripts/sync-extension-libs.sh`), because the background script is a
**classic**, non-module service worker: that's required so it can
`importScripts()` the vendored Argon2id WASM build, which has no ES-module
equivalent of `importScripts()`. Verified directly (not just by reading the
UMD wrapper's environment-detection logic) — a worker loading the real
vendored file via `importScripts()` produces `self.hashwasm` and computes a
real Argon2id hash correctly, and the generated `lib/crypto.js` file's full
`deriveKeys` → wrap/unwrap → encrypt/decrypt pipeline round-trips correctly
in that same worker context.

`background.js` is the **only** place in the extension that ever holds
`vaultKey` or calls the Passvault server — the popup and content script
only exchange `chrome.runtime.sendMessage` calls with it, never touch the
key or the API directly, keeping "where does the key live" answerable in
exactly one place, same as `web/app.js`'s module-level `session` object.
Session state (`accessToken`/`refreshToken`/`vaultKey`, base64, plus a
decrypted-login-items cache) lives in `chrome.storage.session` — RAM-only,
never disk-backed, cleared when the browser closes. That's the MV3-specific
wrinkle the web app doesn't have: a service worker is non-persistent and
Chrome can unload it after ~30s idle, which would silently wipe a plain
in-memory variable; `chrome.storage.session` is the platform's own fix,
surviving a worker restart within the same browser session without ever
touching disk.

Because Passvault is self-hosted with no fixed URL, the extension has no
`host_permissions` baked into its manifest. Instead, an options page asks
the user for their instance's URL and calls `chrome.permissions.request()`
for that one origin, a direct result of the user's own click (required —
Chrome only honors a permission request as an immediate consequence of a
user gesture). A background service worker's `fetch()` calls are exempt
from CORS for any granted `host_permissions` origin — a privileged-context
exemption content-script `fetch()` calls don't get — which is also why no
server-side change was needed to support the extension at all.

**Not implemented yet**: storing/autofilling *passkeys for other sites* —
the actual WebAuthn/FIDO2 software-authenticator implementation
(overriding `navigator.credentials` in a page's MAIN world, generating and
signing with passkey key pairs) is a separate, larger piece of work than
the login/autofill plumbing above, and is the still-open half of the
original browser-extension roadmap motivation. See `extension/README.md`.

## Rate limiting (implemented)

`internal/ratelimit` throttles every guessable-secret endpoint — login,
the 2FA code at login, account recovery, and a password-protected Send's
access check — since nothing else in this codebase defends against an
online attacker just hammering a live endpoint (Argon2id's cost only
helps against an offline attack on a stolen hash). Attempts are counted
per bucket+identifier in a rolling 15-minute window, DB-backed
(`rate_limit_attempts`, swept hourly) rather than in-memory, so a limit
survives a restart. Buckets are namespaced per endpoint *and* per
identifier-kind (email vs. IP vs. one specific Send id) so hammering one
resource can't cross-throttle an unrelated one, and a per-IP ceiling is
always looser than the per-identity one so one flood behind a shared
NAT'd IP can't lock out every other account behind it. Also covers
`Prelogin` and registration — both are otherwise fully public,
unauthenticated endpoints, and registration specifically triggers a real
Argon2id hash server-side on every call, making it a memory/CPU
exhaustion amplifier if left unthrottled under open signup.

Every IP-keyed bucket depends on `clientIP()` correctly identifying the
real client — `X-Forwarded-For` is only trusted when the connection
actually arrived from loopback (the documented nginx-on-the-same-host
deployment shape), and only its right-most, proxy-appended hop is used
even then. A client-supplied header trusted verbatim would let an
attacker manufacture a fresh "IP" on every request just by varying an
arbitrary prefix, silently defeating every rate limit that depends on it.

`Login` also closes a narrower timing side-channel: a nonexistent email
used to return near-instantly (no Argon2id ever runs), while a real
account always pays that cost regardless of whether the password was
right — both paths return the identical `ErrInvalidCredentials`, but at
measurably different speeds. The not-found branch now runs the same-cost
Argon2id comparison against a precomputed, meaningless hash so both
branches take comparable wall-clock time. `Prelogin` has the equivalent
fix in its own shape: a nonexistent email gets a deterministic
HMAC-derived fake salt (stable across repeated calls, keyed by a
per-instance secret in `server_secrets`) instead of a fresh random one
each time — a salt that changed on every call would itself have been the
enumeration oracle this function exists to prevent.

## Recent activity / audit log (implemented)

`GET /v1/audit-log` returns the caller's own `audit_log` rows verbatim
(most recent 200, no pagination yet) — every `audit()` call site across
this codebase already writes only machine-safe labels, never plaintext
secrets, so there's nothing to redact before showing someone their own
account's history. Scoped strictly to `user_id = caller` — never reachable
for anyone else's events. One known gap: a failed login attempt is
recorded with `user_id = NULL` (the account isn't resolved yet at that
point in the code), so failed attempts against your email before a
successful one don't currently appear in your own activity view.

## SMTP / outbound email (implemented)

Emails: emergency-access notifications (invite, accept, confirm, request,
reject, approve, auto-grant, takeover) and account-security notices (2FA
enabled/disabled, a recovery code used). Relay settings (`internal/mailer`)
are a singleton row in Postgres
(`smtp_settings`), editable at runtime from `web/admin.html` — gated by
`PASSVAULT_ADMIN_TOKEN`, not a user session — rather than an env var, so
an operator can set up or change mail delivery without a redeploy. The
SMTP password is stored server-side in plaintext: this is operational
infrastructure config the server must present verbatim to a mail relay,
the same trust class as `PASSVAULT_DB_DSN`, and explicitly **not** part of
the zero-knowledge boundary — nothing about it is wrapped under any
user's `vaultKey`, and it never appears in a response to a regular user.
A failed send never fails the action that triggered it (an emergency
access request still gets recorded even if the grantor's mail relay is
down) — it's logged server-side for the operator instead.

## What "opaque to the server" actually means in the schema

| Column | Contents | Server can... |
|---|---|---|
| `users.auth_hash` | Argon2id-2(authKey) | compare, never reverse |
| `users.wrapped_vault_key` | AES-GCM(wrapKey, vaultKey) | store/return verbatim |
| `users.wrapped_x25519_private_key` | AES-GCM(vaultKey, privKey) | store/return verbatim |
| `ciphers.wrapped_item_key` | AES-GCM(vaultKey, itemKey) | store/return verbatim |
| `ciphers.encrypted_blob` | AES-GCM(itemKey, JSON) | store/return verbatim |
| `sends.wrapped_send_key` | AES-GCM(vaultKey, sendKey) | store/return verbatim |
| `sends.encrypted_content` / `encrypted_filename` | AES-GCM(sendKey, ...) | store/return verbatim |
| `sends.password_hash` | Argon2id-2(password) | compare, never reverse |
| `emergency_access.wrapped_vault_key_for_grantee` | AES-GCM(emergencyWrapKey, vaultKey) | store/return verbatim |
| `users.wrapped_email_alias_api_key` | AES-GCM(vaultKey, JSON) | store/return verbatim |
| `smtp_settings.password` | plaintext | **not opaque — operational config, not user data** |
| `users.totp_2fa_secret` | plaintext | **not opaque — must actively verify codes, see Account 2FA above** |
| `recovery_codes.code_hash` | SHA-256(code) | compare, never reverse |
| `users.recovery_code_hash` | SHA-256(recoveryAuthKey) | compare, never reverse |
| `users.wrapped_vault_key_for_recovery` | AES-GCM(recoveryWrapKey, vaultKey) | store/return verbatim |

No row in any of these columns can be turned into plaintext without the
user's master password having been entered on a client at some point in the
causal chain. A full database dump (`internal/db/db.go`'s schema) is not a
vault compromise on its own — see SECURITY.md for how to report it if you
find a way to make that claim false.
